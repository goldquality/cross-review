# cross-review

Кросс-ревью MR силами команды. Участник просит ревью своего MR, брокер раздаёт его половине свободных
коллег, а их клиенты запускают у себя ту команду ревью, которую каждый настроил сам. Например,
`./dev review <LINK>`, который гоняет Claude Code, или свой скрипт с Codex.

```
клиент Васи ──запрос: ссылка на MR──▶ брокер (Docker, SQLite)
                                        │ ⌈50%⌉ подходящих
клиент Пети ◀── задание: только ссылка ─┤   клиенты сами опрашивают брокер
клиент Маши ◀───────────────────────────┘
   └ проверить ссылку → своя команда → код выхода → брокер: +1 балл
```

cross-review не знает, как делается ревью. Брокер передаёт только ссылку на MR. Команда, пути и
доступы к GitLab, Claude и Codex остаются на машине участника.

## Правила

- Запрос ревью стоит 1 балл, опубликованное ревью приносит 1 балл. На старте у участника 2 балла.
  Балл за запрос не возвращается, даже если ревью не состоялось.
- Просить можно, только когда клиент запущен, проект подключён и баланс не меньше 1.
- На запрос ревьюят ⌈50%⌉ подходящих участников, параллельно. Подходящий: клиент онлайн, нет паузы,
  нет другого задания, проект подключён, и это не тот, кто просит. Первыми получают задание те, кто
  дольше всех его не получал.
- Каждый ревьюер публикует сам, от своего аккаунта. Дубли между ревьюерами никто не ищет: с ними
  разбирается автор MR.
- Ревью упало, клиент пропал на 3 минуты или ревью идёт дольше 60 минут — задание один раз уходит
  следующему подходящему участнику.
- Если подходящих нет, запрос ждёт до 24 часов.
- Пауза — на 1, 3, 6, 12 или 24 часа. На паузе задания не приходят, а просить ревью можно.

## Брокер

Брокеру нужна VPS с доменом. Caddy сам получает сертификат.

```sh
git clone git@github.com:goldquality/cross-review.git && cd cross-review
DOMAIN=review.example.com docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml logs broker        # приглашение при первом старте
```

Управление:

```sh
docker compose -f deploy/docker-compose.yml exec broker broker invite            # показать приглашение
docker compose -f deploy/docker-compose.yml exec broker broker invite --rotate   # заменить; ключи живут
docker compose -f deploy/docker-compose.yml exec broker broker members           # баллы, активность
docker compose -f deploy/docker-compose.yml exec broker broker revoke "Петя"     # отозвать ключ
docker compose -f deploy/docker-compose.yml exec broker broker grant "Петя" 3    # начислить баллы
```

Готовый образ — `ghcr.io/goldquality/cross-review-broker` с тегами `vX.Y.Z`, `latest` и `sha-<коммит>`.
За своим прокси вместо Caddy брокеру нужны переменные:
- `BROKER_PUBLIC_URL` — внешний адрес;
- `BROKER_TRUST_PROXY=1` — брать адрес клиента из `X-Forwarded-For`;
- `HEALTH_DRAIN_FILE` — при деплое без простоя: пока этот файл есть, `/healthz` отвечает 503.

Приглашение — общее для команды. При первом подключении клиент меняет его на личный ключ, поэтому
отозвать можно одного человека, а смена приглашения не трогает выданные ключи.

## Клиент

Скачай архив своей ОС со страницы релизов и запусти `cross-review`. Появится иконка в трее, клиент
спросит адрес брокера, приглашение и имя, потом предложит подключить проект.

| ОС | Первый запуск |
|---|---|
| macOS | Сборка не подписана: `xattr -d com.apple.quarantine cross-review` или «Открыть» в контекстном меню Finder. |
| Windows | SmartScreen: «Подробнее» → «Выполнить в любом случае». |
| Linux | Нужны панель с поддержкой StatusNotifier (GNOME — расширение AppIndicator), `zenity` или `kdialog` для окон и `xclip` или `wl-clipboard` для буфера. |

В меню трея:
- попросить ревью MR по ссылке из буфера (в меню виден баланс);
- мои запросы;
- текущее задание: лог, остановить;
- проекты;
- пауза;
- автозапуск при входе в систему.

### Проект

Проект — это один репо GitLab. Добавляется так:

1. Ввести адрес репо, например `https://gitlab.example.com/acme/api`.
2. Клиент ищет клоны с таким remote в домашней папке на глубину до 5 уровней. ssh- и https-адреса
   одного репо совпадают.
3. Выбрать клон из списка или указать папку вручную.
4. Выбрать, где запускать команду. По умолчанию — в папке клона.
5. Ввести команду, например `./dev review <LINK>`.

Если команда живёт в соседнем репо, нужна отдельная папка запуска. Например, MR приходят в
`api` и `web`, а `./dev review` лежит в общем репо `devtools`. Значит, это два проекта с
папкой запуска `devtools` и одной командой.

### Договор с командой ревью

- `<LINK>` заменяется каноничной ссылкой `https://хост/группа/проект/-/merge_requests/N`.
- Ссылка внутри своего аргумента: `--url=<LINK>` тоже работает.
- Запуск без шелла, в папке запуска, stdin закрыт, PATH взят из логин-шелла участника.
- Код выхода 0 — ревью опубликовано, +1 балл. Любой другой код — неудача, задание уйдёт другому.
- Рабочую копию команда не трогает: `./dev review` ревьюит в своём worktree.
- Через 60 минут или по «Остановить» дерево процессов убивается.

## Безопасность

- Брокер не присылает ничего исполняемого. Клиент разбирает ссылку заново: только https,
  символы `[A-Za-z0-9._/:-]`, без логина, порта, query и fragment, репо должен быть среди
  подключённых. Дальше клиент собирает каноничную ссылку из частей, так что даже `.bat` на Windows
  не получит управляющих символов.
- Ключи на брокере хранятся хэшем. Конфиг клиента лежит с правами 0600:
  `~/Library/Application Support/cross-review`, `~/.config/cross-review` или
  `%AppData%\cross-review`.
- Брокер хранит имена, входы GitLab, ссылки на MR и баллы. Кода и чужих доступов у него нет.
  Частота запросов на ключ ограничена.

## Командная строка

```
cross-review join <адрес брокера> <приглашение> --name Имя [--gitlab вход]
cross-review projects | projects scan <репо> | projects add <репо> --clone П [--workdir П] --command "…<LINK>" | projects remove <репо>
cross-review request <ссылка на MR> | requests | pause <1|3|6|12|24|off> | status
cross-review run <ссылка на MR>     прогнать свою команду локально, без брокера
cross-review daemon                 без трея: для сервера или проверки
cross-review install | uninstall    автозапуск
```

`CROSS_REVIEW_HOME` задаёт папку клиента. Так на одной машине можно запустить двух клиентов.

## Разработка

```sh
go test ./...                       # брокер, ссылки, клиент, сквозной круг
docker build -f deploy/Dockerfile -t cross-review-broker:dev .
docker run -d -p 18080:8080 cross-review-broker:dev   # http://localhost разрешён клиенту для проверки
```

Релиз — тег `v*`. Workflow собирает клиент для macOS (universal, на маке из-за cgo), Linux и Windows
и публикует образ брокера в `ghcr.io/goldquality/cross-review-broker`.
