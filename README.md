# cross-review

Кросс-ревью MR силами команды. Участник просит ревью своего MR, брокер раздаёт его половине свободных
коллег, а их клиенты запускают у себя ту команду ревью, которую каждый настроил сам. Например,
`./dev review <LINK>`, который гоняет Claude Code, или свой скрипт с Codex.

```
клиент Васи ──запрос: ссылка на MR──▶ брокер (Docker, SQLite)
                                        │ ⌈50%⌉ подходящих
клиент Пети ◀── задание: только ссылка ─┤   клиенты сами опрашивают брокер
клиент Маши ◀───────────────────────────┘
   └ проверить ссылку → своя команда → код выхода → брокер: +1 балл
```

cross-review не знает, как делается ревью. Брокер передаёт только ссылку на MR. Команда, пути и
доступы к GitLab, Claude и Codex остаются на машине участника.

## Правила

- Запрос ревью стоит 1 балл, опубликованное ревью приносит 1 балл. На старте у участника 2 балла.
  Балл за запрос не возвращается, даже если ревью не состоялось.
- Просить можно, только когда клиент запущен, проект подключён и разрешён на брокере, а баланс не
  меньше 1. В работе одновременно — не больше 5 запросов участника.
- На запрос ревьюят ⌈50%⌉ подходящих участников, параллельно. Подходящий: клиент онлайн, нет паузы,
  нет другого задания, проект подключён, и это не тот, кто просит. Первыми получают задание те, кто
  дольше всех его не получал.
- Каждый ревьюер публикует сам, от своего аккаунта. Дубли между ревьюерами никто не ищет: с ними
  разбирается автор MR.
- Пришедшее задание участник принимает или отклоняет в окне трея. Отказ или молчание 5 минут
  отдают задание следующему подходящему; отказавшемуся задание по этому запросу больше не придёт.
  `daemon` спросить некого, поэтому он принимает задания сам.
- Ревью упало, клиент пропал на 3 минуты или ревью идёт дольше 60 минут с момента принятия — задание
  один раз уходит следующему подходящему участнику.
- Если подходящих нет, запрос ждёт до 24 часов.
- Пауза — на 1, 3, 6, 12 или 24 часа. На паузе задания не приходят, а просить ревью можно.

## Брокер

Брокеру нужна VPS с доменом. Caddy сам получает сертификат.

```sh
git clone git@github.com:goldquality/cross-review.git && cd cross-review
DOMAIN=review.example.com docker compose -f deploy/docker-compose.yml up -d --build
alias broker='docker compose -f deploy/docker-compose.yml exec broker broker'
broker repos add https://gitlab.example.com/acme/api   # репо, по которым команда ревьюит
broker invite "Петя"                                   # личное приглашение
```

Управление:

```sh
broker invite "Петя"        # личное приглашение: одноразовое, на 7 дней, показывается один раз
broker invites              # неиспользованные приглашения
broker members              # баллы, активность, версии клиентов
broker revoke "Петя"        # отозвать ключ; имя остаётся за участником
broker grant "Петя" 3       # начислить баллы, n < 0 — списать
broker repos                # разрешённые репо; add <адрес> | remove <адрес>
broker snapshot             # снимок базы сейчас
```

Приглашение — личное, на имя. Его вписывают в файл настроек участника, а клиент при первом
подключении меняет приглашение на ключ. Имя в команде задаёт приглашение, а не клиент; имена из
разных алфавитов, неотличимые на глаз (латинская и кириллическая «А»), брокер не выдаёт.

Новое приглашение на то же имя отменяет прежнее. Если у участника уже есть ключ, вход по новому
приглашению заменит ключ, а баллы останутся. Так возвращают того, кто сменил компьютер или потерял
папку клиента, и того, кого отозвали.

Ревьюить и просить ревью можно только в разрешённых репо (`broker repos`). Репо из настроек
участника, которого нет в списке, клиент покажет как «брокер не разрешает».

Готовый образ — `ghcr.io/goldquality/cross-review-broker` с тегами `vX.Y.Z`, `latest` и `sha-<коммит>`.
Переменные:
- `BROKER_PUBLIC_URL` — внешний адрес, печатается рядом с приглашением;
- `BROKER_TRUST_PROXY=1` — брокер за прокси в частной сети Docker. Только запросам из частных
  сетей брокер верит `X-Forwarded-For`. Точнее — `BROKER_TRUSTED_PROXIES`: подсети прокси через
  запятую;
- `HEALTH_DRAIN_FILE` — при деплое без простоя: пока этот файл есть, `/healthz` отвечает 503;
- `BROKER_SNAPSHOT` — снимок базы для бэкапа, по умолчанию `/data/snapshot.db`, `-` — не писать.

### Бэкап

Раз в 15 минут брокер пишет целостную копию базы в `/data/snapshot.db`. Бэкапить нужно её: живые
файлы `broker.db` и `broker.db-wal` при копировании по очереди попадают в бэкап из разных моментов.
Восстановление: остановить брокер, положить снимок на место `broker.db`, удалить `broker.db-wal` и
`broker.db-shm`, запустить.

## Клиент

1. Скачай архив своей ОС со страницы релизов.
2. Положи в домашнюю папку файл настроек `cross-review.yaml`. Обычно его присылает администратор
   брокера: с адресом брокера, твоим личным приглашением и проектами.
3. Запусти `cross-review`: появится иконка в трее.

Если файла нет, клиент при запуске создаст шаблон и откроет его в редакторе.

| ОС | Первый запуск |
|---|---|
| macOS | Сборка не подписана: `xattr -d com.apple.quarantine cross-review` или «Открыть» в контекстном меню Finder. |
| Windows | SmartScreen: «Подробнее» → «Выполнить в любом случае». |
| Linux | Нужны панель с поддержкой StatusNotifier (GNOME — расширение AppIndicator), `zenity` или `kdialog` для окон и уведомлений и `xclip` или `wl-clipboard` для буфера. |

В меню трея:
- попросить ревью MR по ссылке из буфера (в меню виден баланс);
- мои запросы;
- кто из команды онлайн: свободен, ревьюит или на паузе;
- топ-5 по баллам;
- текущее задание: лог, остановить;
- проекты из настроек;
- пауза;
- «Настройки…» — открыть файл настроек в редакторе;
- автозапуск при входе в систему.

### Файл настроек

```yaml
broker: https://review.example.com
invite: inv_…              # личное приглашение; нужно только при первом подключении

# команда и папка запуска для всех проектов, у которых не указаны свои
command: ./dev review <LINK>
workdir: ~/projects/devtools

projects:
  - repo: https://gitlab.example.com/acme/api
  - repo: git@gitlab.example.com:acme/web.git
  - repo: https://gitlab.example.com/acme/mobile
    workdir: ~/projects/mobile
    command: ./review.sh --url=<LINK>
```

- `projects` — репо, чьи MR ты ревьюишь и в которых просишь ревью сам. ssh- и https-адреса одного
  репо равнозначны.
- `workdir` — папка, где запускается команда; `~` — домашняя папка. Если команда лежит в общем репо,
  как `./dev review` в `devtools`, папка у всех проектов одна.
- Клиент перечитывает файл сам после сохранения. Если в файле ошибка, трей покажет её, а клиент
  продолжит работать по последним исправным настройкам.
- При первом запуске клиент меняет приглашение на ключ. Ключ и пауза хранятся отдельно, в папке
  клиента; файл настроек клиент не меняет. Если сменить `broker`, клиент подключится к новому брокеру
  по `invite`: для этого нужно новое приглашение, старое уже использовано.

### Обновление

Сам клиент не обновляется. Когда выходит новая версия, трей один раз присылает уведомление и
показывает в меню «Вышла vX.Y.Z — скачать». Чтобы обновиться:

1. скачать архив;
2. выйти из трея;
3. заменить файл `cross-review` новым;
4. запустить клиент снова.

Настройки и ключ при этом сохраняются.

### Договор с командой ревью

- `<LINK>` заменяется каноничной ссылкой `https://хост/группа/проект/-/merge_requests/N`.
- Ссылка внутри своего аргумента: `--url=<LINK>` тоже работает.
- Запуск без шелла, в папке запуска, stdin закрыт, PATH взят из логин-шелла участника.
- Команда запускается, только когда участник нажал «Принять» в окне с вопросом. В окне — кто
  просит, ссылка на MR, кнопка «Открыть MR» и команда, которая запустится.
- Код выхода 0 — ревью опубликовано, +1 балл. Любой другой код — неудача, задание уйдёт другому.
- Рабочую копию команда не трогает: `./dev review` ревьюит в своём worktree.
- Через 60 минут или по «Остановить» дерево процессов убивается.
- Команда закончилась, а её фоновый потомок держит вывод открытым: клиент ждёт 10 секунд и засчитывает
  код выхода команды.
- Хвост вывода уходит брокеру только при неудаче; вывод удачного ревью остаётся на машине.

## Безопасность

- Брокер не присылает ничего исполняемого. Клиент разбирает ссылку заново: только https,
  символы `[A-Za-z0-9._/:-]`, без логина, порта, query и fragment, репо должен быть среди
  подключённых. Дальше клиент собирает каноничную ссылку из частей, так что даже `.bat` на Windows
  не получит управляющих символов.
- Ни одна команда не запускается без «Принять» в окне трея. Режим `daemon` принимает задания сам.
- Строки от брокера (уведомления, имена, тексты ошибок) клиент чистит перед показом: на Windows
  zenity вставляет текст уведомления в скрипт PowerShell, на Linux тело уведомления понимает
  разметку, в терминале работают управляющие последовательности.
- Ключи и приглашения на брокере хранятся хэшем. Ключ клиента лежит в `state.json` с правами 0600,
  в папке клиента: `~/Library/Application Support/cross-review`, `~/.config/cross-review` или
  `%AppData%\cross-review`. Редиректам клиент не следует: ключ не уйдёт по http или на чужой хост.
- Брокер хранит имена, ссылки на MR, баллы и хвосты вывода неудачных ревью; чужих доступов у него
  нет. Частота запросов на ключ ограничена, неверные ключи — по адресу, долгий опрос — один на
  участника.
- Баллы держатся на доверии: код выхода 0 — +1. Против накрутки — личные приглашения (без
  аккаунтов-клонов), список разрешённых репо (без своего репо «для баллов») и окно «Принять».

## Командная строка

```
cross-review config                 где файл настроек и что в нём не так; нет файла — создать шаблон
cross-review projects               проекты из настроек
cross-review request <ссылка на MR> | requests | pause <1|3|6|12|24|off> | status
cross-review run <ссылка на MR>     прогнать свою команду локально, без брокера
cross-review daemon                 без трея: для сервера или проверки
cross-review install | uninstall    автозапуск
```

`CROSS_REVIEW_HOME` задаёт папку клиента, и файл настроек тогда лежит в ней. Так на одной машине
можно запустить двух клиентов.

## Разработка

```sh
go test ./...                       # брокер, ссылки, клиент, сквозной круг
docker build -f deploy/Dockerfile -t cross-review-broker:dev .
docker run -d -p 18080:8080 cross-review-broker:dev   # http://localhost разрешён клиенту для проверки
```

Релиз — тег `v*`. Workflow собирает клиент для macOS (universal, на маке из-за cgo), Linux и Windows
и публикует образ брокера в `ghcr.io/goldquality/cross-review-broker`, а `docker-compose.yml`
брокера кладёт в файлы релиза. К файлам релиза прилагаются
`SHA256SUMS` и подпись происхождения: `gh attestation verify cross-review-macos.zip -R
goldquality/cross-review`. Actions и базовые образы закреплены по SHA, обновляет их Dependabot.

Брокер собирается с номером версии из тега и сообщает его клиентам. Поэтому, как только брокер
нового релиза задеплоен, клиенты со старой версией подсказывают обновиться. Если брокер меняется
несовместимо со старыми клиентами, порядок обратный: сначала релиз и обновление клиентов, потом
деплой брокера.
